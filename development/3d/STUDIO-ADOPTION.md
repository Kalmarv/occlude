# Main Studio render publication

The previous client/worker protocol allowed a completed obsolete render to update the preview, while the worker had already replaced the committed plan. A newer sketch failure then left the previous displayed plan unexportable. The new hardware-browser reproduction fails against deployed `faca614` with `stale plan: the drawing changed` when exporting the displayed result while a completed render reply is held in transit.

RenderClient now requests staged publication. The worker retains at most one completed candidate alongside its committed drawing/run/plan/geometry snapshot. The client decodes and validates the current input revision before sending `accept-render`; that message precedes exports from the resolved consumer. Obsolete or undecodable replies send `discard-render` and resolve null/reject without replacing committed state. The candidate's source, paper/pen settings and backend capture belong to its completed execution. Direct low-level worker requests retain immediate publication unless they opt into the staged protocol.

Ordinary sketch runs now receive cooperative AbortSignals, as camera commits already did. Editor changes invalidate in-flight/queued renders immediately, before the 150 ms replacement debounce. The client also rejects successful obsolete replies that were already in transit. Main Studio takes the run revision before asynchronous source preparation and checks it after emission, so an older compilation cannot submit after a newer request. Only accepted current results may update the preview, seed, probes, plan and construction metadata. Messages from a replaced worker cannot settle a new worker's pending requests.

Four client tests cover late successful obsolete replies followed by replacement failure, decode-before-accept ordering and subsequent exports, invalidated input revisions, cancellation before a replacement exists, decode failures and camera cancellation without a worker restart.

`tools/verify-adoption.mjs` uses Playwright on the actual main Studio and a nonfallback NVIDIA GPU. It deliberately holds a completed normal-render reply, confirms the previous SVG remains exportable before acceptance, edits the source to a failing sketch, then releases the late reply. It verifies explicit discard, absence of accept, and unchanged plan/SVG after failure. It repeats the scenario with an explored camera commit. The source server passes both cases; the previous deployed bundle fails the intended stale-plan assertion. Initial harness setup omitted a required line set and was corrected before these comparisons; that setup failure is not counted as an application regression.

This closes the tested successful-reply-in-transit adoption race. It is not full lifecycle signoff: hard worker restart/export recovery, device loss and every upload/dispatch/readback/refinement cancellation boundary remain in the working audit. Camera-control workflow/API choices remain deferred at the user's request.
